# 执行计划

这份计划把当前的 `P0 / P1 / P2` backlog 再往前推一步，变成一个更实际的近期推进顺序。

它比路线图更窄。路线图回答“方向是什么”，这份文档回答“最近先做什么，避免每周都重新讨论一次产品方向”。

## 当前策略

接下来按这个顺序推进：

1. 先把“信号与电路 -> 器件工坊 -> 逻辑与存储 -> 机器 -> 算法”的五单元主线写清楚，并同步到大厅信息架构
2. 把电路工作台和教学闭环作为信号与电路层做稳
3. 再把 beta 发布前的不确定项逐个压掉
4. 然后继续推进机器层融合实现，优先接通 Rust/WASM 核心
5. 最后再评估桌面端、硬件联动这类更大的扩展赌注

## 阶段 A：核心稳定

目标：让当前工作台进入一个更安全、可持续迭代的状态。

### 重点

- 工作台交互稳定性
- 小屏和触控可靠性
- 仿真回归信心
- 本地记录、导入导出和恢复体验
- 围绕大页面组件继续做架构拆分

### 期望产出

- 桌面端和移动端的主要工作台流程更稳定
- 自动化检查覆盖最容易出问题的仿真和持久化路径
- 即使云端能力异常，应用也仍然可用
- 后续新功能不必继续把逻辑堆回一个大页面里

### 候选任务

- 为电路求值、工作台编码、实体搭建输出和实验报告格式补更多测试
- 把任意旋转、旋转后端子连线、图片导出和小屏 HUD 放在一起复测
- 降低导入失败、恢复失败、无效分享链接、异常本地记录这些场景的困惑感
- 继续把主工作台页面里的状态逻辑往 composable 或 lib 模块拆

### 退出条件

- 搭建、连线、保存、恢复、分享、完成课程这些主流程没有明显阻塞项
- 回归信心比现在高，而不只是功能数量更多
- 改工作台功能时，对“会不会顺手搞坏别处”的担心明显下降

## 阶段 B：公开测试版收口

目标：在扩大可见度之前，把最大的未知风险先压下来。

### 重点

- 真机 QA
- 线上 PWA 验证
- 分享链接验证
- 线上云端记录验证
- 发布说明和公开入口决策

### 期望产出

- 这个应用已经能公开给人用，而不是每个基础流程都要先道歉
- 未登录用户仍然有完整路径
- 云端功能要么经过验证，要么明确标注限制
- beta 范围不再继续漂移

### 候选任务

- 按 QA 清单跑手机竖屏、手机横屏、iPad 横屏和桌面回归
- 验证 PWA 安装、离线再次打开、更新检查、线上 manifest 和 service worker
- 验证分享链接在新浏览器和移动端的恢复效果
- 验证 Supabase 登录和记录流程，或者明确把云端能力标成 beta 限制
- 收口公开测试版定位、已知限制和反馈入口文案

### 退出条件

- public beta 的阻塞项已经已知且有限
- 是否发布取决于验证结果，而不是再加一个新功能
- 项目 owner 可以基于证据决定发还是不发

## 阶段 C：产品一致性

目标：让项目更像一个清晰产品，而不是一组有意思的模块拼在一起。

### 重点

- 维修任务系统扩展
- 报告和实体搭建交付物增强
- 分享和模板体验
- 大厅信息架构：信号与电路、器件工坊、逻辑与存储、机器、算法、探索实验区
- 更清晰的产品表达

### 期望产出

- 维修任务更像一条明确的学习路径，而不是旁边的一个模式
- 实验报告和搭建清单在应用外也更有用
- 大厅页能明显区分五个主线单元与探索实验区
- 用户在第一屏就更容易理解这个项目是干什么的

### 候选任务

- 增加更多维修任务，并补出更清晰的难度梯度和复查循环
- 提升实验报告的可读性和打印价值
- 提升实体搭建清单的措辞、分组和导出质量
- 增加或整理课程/演示模板
- 继续打磨大厅的主线学习路径和探索实验区，并把机器层预览接到真实 Rust/WASM bridge

### 退出条件

- 更容易一句话讲清项目的核心用途
- 主线入口比支线实验更强
- 教学流和维修流显得更有意图，而不是自然长歪出来的

## 阶段 D：受控扩展

目标：在不扰乱主产品的前提下，探索更大的机会。

### 重点

- 更多元器件与配套课程
- Rust/WASM 机器核心融合
- 面向老师的工作流试验
- Tauri 桌面端评估
- 硬件联动探索

### 决策门槛

- 在 Web/PWA 核心稳定前，不启动 Tauri 改造
- 机器层优先走 Rust core -> WASM bridge -> Vue/TypeScript UI，而不是直接把主产品改成桌面优先
- 在没有明确实体设备工作流之前，不启动硬件联动
- 不让实验区扩展速度超过主线产品稳定速度

## 使用原则

- 有疑问时，优先选择“提高可发布信心”，而不是“再加一个功能”
- 能强化“信号 -> 电路 -> 机器 -> 算法”主线的需求优先于支线实验
- 每一个扩展赌注都应该回答一个明确的产品问题，而不只是技术好奇心
- 如果一个任务说不清属于哪个阶段，那它大概率应该先回到想法池
